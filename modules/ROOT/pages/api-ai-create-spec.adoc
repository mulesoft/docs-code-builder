= Creating API Specs with AI
:page-deployment-options: cloud-ide, desktop-ide

The AI-powered API Specification feature enables you to generate and mock API specifications from natural language prompts. This feature reduces the time spent on API design by simplifying the creation of syntax-heavy specifications. You can access the feature after creating an API project that's in the supported RAML 1.0 or OAS 3.0 format and then opening MuleSoft Dev Agent.

[[before-you-begin]]
== Before You Begin

Before you start creating your API spec:

* xref:start-acb.adoc[Set up and access the web or desktop IDE].
* Make sure you have the xref:start-configure-permissions.adoc#permissions[required Anypoint Code Builder permissions].
* Install Node.js version 20 (v20.19.4).  
  For more information, see https://nodejs.org/en/download[Download Node.js].
* Log in to Anypoint Code Builder with your Anypoint Platform credentials.
* xref:des-create-api-specs.adoc[Create an API spec project] in Anypoint Code Builder in the supported RAML 1.0 or OAS 3.0 format, and then select a business group.

[[design-api]]
== Design an API Spec with AI

To design an API spec with MuleSoft Dev Agent:

. Open MuleSoft Dev Agent from the toolbar or from the *Build your enterprise with AI* card in the canvas.
. Enter a prompt that describes your API specification.
+
Include these required details and consider including optional details to generate a more precise spec:
+
[%collapsible]
.Base Details
====
Optionally provide the API name, version, and description.
====
+
[%collapsible]
.Security Details
====
Include a required security scheme of type Oauth 1.0, Oauth 2.0, Basic Authentication, Digest Authentication, or Pass Through.

**** For Basic Authentication, Digest Authentication, or Pass Through, specify responses, query parameters, and headers.
**** For Oauth 1.0 or 2.0, specify responses, query parameters, headers, and settings.
***** Settings for Oauth 1.0 can be of type `authorizationUri`, `requestTokenUri`, `tokenCredentialsUri`, or signatures.
***** Settings for Oauth 2.0 can be of type `authorizationUri`, `requestTokenUri`, or `authorizationGrants`.
====
+
[%collapsible]
.Resources and Methods
====
Each resource can include one or more of the following methods:

* GET
* POST
* PUT
* PATCH
* DELETE
* HEAD
* OPTIONS

For GET and HEAD methods, you can include a summary, responses, requests, and query or header parameters.

For POST, PUT, PATCH, and OPTIONS methods, you can include a summary, responses, requests, body, and query or header parameters.

*Response Requirements*

Responses must include the status code and description. Response bodies are optional and can include a description, type, media type, and example.

*Request Requirements*

Requests must include a description and body.

*Header Requirements*

Headers must include the name, whether it's required, and one of the following types:

* Array
* Boolean
* Date only
* DateTime
* DateTime only
* File
* nil
* Number
* Object
* String
* Time only

Optionally, provide a description, format, minimum and maximum length, default value, and example for the header.

*Query Parameter Requirements*

Query parameters must include the name, whether it's required, and one of the following types:

* Array
* Boolean
* Date only
* DateTime
* DateTime only
* File
* nil
* Number
* Object
* String
* Time only 

Optionally, provide a description, format, minimum and maximum length, default value, and example for the query parameter.
====
. Submit your prompt in MuleSoft Dev Agent.  
+
Dev Agent generates a validated API specification based on your input.
. Review the generated specification. 
. Click *Replace* to insert the generated API spec into your project. All file content is replaced by the inserted code.
+
You can also copy the generated API spec to your clipboard by clicking *Copy*.

[NOTE]
Governance isn't included in the validation.

[[rules-workflows]]
== Define Rules and Workflows

You can guide Dev Agent’s behavior by creating reusable rules and workflows:

* *Rules* – Define constraints or guidelines for how the API spec should be generated.  
  For example, enforce a naming convention or require consistent error handling.  
  Rules can be defined at the workspace or global level.

* *Workflows* – Create a series of steps that Dev Agent executes as a predefined action.  
  Workflows are invoked using slash commands in the Dev Agent panel.

[[context-files]]
== Provide Additional Context

You can add supporting files to help Dev Agent generate more accurate API specifications:

* Upload requirement files, such as `requirements.txt`.
* Provide additional folders or specific project files.
* Include terminal input or outputs.  

These files are used as contextual references during API generation.

[[settings]]
== Dev Agent Settings

You can control how Dev Agent interacts with your project through the settings panel:

* *Read project files*: Allow Dev Agent to read project files for context.  
* *Edit project files*: Allow Dev Agent to write changes directly to your project.  
* *Auto-approve*: Enable to apply changes automatically without prompting for confirmation.  +
If *Auto-approve* is disabled, Dev Agent will request your approval before making any file changes.
